> **Альтернатива яку відкинули** (якщо була). За потреби — додаткові рядки
> на кшталт **Коли прийнято** чи **Реалізація** з номером issue.
> Оновлюється кожного разу коли приймається рішення яке впливає на архітектуру.
>
> **Заголовок — до 8 слів і без дужок.** Звʼязок із попереднім записом іде
> окремим полем, бо з нього будується зміст: `**Уточнює:**`, `**Виправляє:**`,
> `**Оновлює:**`, `**Звужує:**`, `**Виконує:**` — на новому записі, а
> `**Виправлено:**` — на тому, що застарів. Назви полів фіксовані:

> випаде зі змісту. Після зміни заголовків — `npm run toc`.
>
> Записи **можна** редагувати; append-only знято разом із ревізією обсягу
> (див. «Редакція документації: append-only знято, зміст генерується»).
> Виправлення все одно лишається окремим записом, а не переписуванням
> старого, — ланцюжок рішень має бути видно.

## Tooling & Agent Setup

### AGENTS.md як SSOT, .cursor/rules — короткі витяжки

**Рішення:** `AGENTS.md` — єдине повне джерело правил (single source of truth) для агентів. `.cursor/rules/*.mdc` — короткі витяжки з `globs`, підвантажуються тільки для релевантних файлів.
**Чому:** уникнути дублювання одних і тих же правил в кількох файлах і ризику розсинхронізації (drift). Економія токенів — Cursor не тягне всі правила в кожен запит.

### Docker Desktop — all-users install

**Рішення:** Docker Desktop встановлений в режимі "install for all users", другий розробник доданий в групу `docker-users`.
**Чому:** контейнери і образи мають бути доступні обом розробникам на одній фізичній машині (Windows, спільний ПК).

### Імпорт AGENTS.md замість ручних витяжок

**Оновлює:** запис вище.
**Рішення:** конфіги агентів більше не тримають ручних витяжок з `AGENTS.md` — тільки нативний `@file`-імпорт. `CLAUDE.md` у корені імпортує `AGENTS.md` для Claude Code.
**Чому:** ревізія показала, що витяжки розійшлися з оригіналом: інструкції «додай запис у DECISIONS.md» і «познач пункт у PROGRESS.md» були в `AGENTS.md`, але були відсутні в усіх `.mdc`-файлах. Тобто сесія в Cursor чи Antigravity ніколи не отримувала команди вести ці два документи. Ручна синхронізація кількох копій одних правил ненадійна навіть в одноосібному проєкті — імпорт прибирає друге джерело правди фізично, а не дисципліною.
**Компроміс:** завжди-активний конфіг тепер підвантажує весь `AGENTS.md` у кожен запит, а не умовно релевантні частини. При поточному розмірі це прийнятна ціна; якщо файл суттєво виросте — можна повернути glob-based підвантаження, розбивши його на імпортовані частини.
**Альтернатива яку відкинули:** лишити тематичні файли, перетворивши кожен на окремий імпорт того самого `AGENTS.md`. Відкинули — вони додавали б той самий вміст ще раз, а для `src/routes/**` потенційно двічі, без жодної нової інформації.

### Розділення `AGENTS.md` на завжди-контекст і ситуативні правила

**Виконує:** «Імпорт AGENTS.md замість ручних витяжок» вище.
**Рішення:** `AGENTS.md` лишає лише те, що формує код у момент написання (стек, стандарти, Handler Pattern, обробка помилок, БД, безпека, тестування, покажчик на конвенції). Ситуативні правила переїхали: `task-workflow` і `pr-workflow` — у `.claude/skills/` (за потреби), документаційні тригери — у `.claude/hooks/doc-rules.cjs` (на правці відповідного файлу). Хуки й скіли лежать у **проєктному** `.claude/` і комітяться; поза git лишається тільки `.claude/settings.local.json`.
**Чому:** головна причина — не розмір, а **дублювання**. Секції «When you make an architectural decision» і «When you introduce a backend concept» переказували формати записів, уже описані в шапці `docs/DECISIONS.md` і в «Формат запису» `docs/LEARNING.md`. Два джерела правди для одного формату — та сама хвороба, що вже двічі вдарила: витяжки в `.cursor/rules` розійшлися з `AGENTS.md`, а секція статусу в `ONBOARDING.md` — з README. Розмір — наслідок: 254 → 150 рядків.
**Компроміс:** правило в скілі застосовується, лише якщо модель вирішить цей скіл підвантажити, — тобто залежить від якості `description`. Це слабша гарантія, ніж «завантажено завжди». Приймаємо для `task-workflow` і `pr-workflow`, бо момент їх застосування впізнаваний із запиту, і не приймаємо для Handler Pattern чи правил помилок — вони лишились у `AGENTS.md`.
**Чому хук для документаційних тригерів:** правило в тексті діє, лише якщо агент його прочитав і згадав; хук спрацьовує завжди. Це третій шар поверх двох наявних (правило в SSOT, чекбокс у PR-шаблоні) і єдиний, що не залежить від уваги. Тому ж він мовчить за замовчуванням: для роутів спрацьовує лише на **створенні** файлу (`Write` **і** відсутність у git-індексі), інакше нагадував би двадцять разів за фічу, після чого його перестали б читати.
**Чого хук навмисно не робить:** не має тригера на `src/db/migrations/` — ці файли створює drizzle-kit через Bash, тож `PostToolUse` з matcher `Write|Edit` їх ніколи не побачить, і правило виглядало б робочим, не спрацювавши жодного разу. Нагадування про `LEARNING.md` натомість вкладене в правило для схеми, яке спрацьовує на крок раніше — на правці, що робить міграцію потрібною.
**Альтернатива яку відкинули:** (1) розбити `AGENTS.md` на файли з glob-based підвантаженням — Cursor і Antigravity мають різні механізми глобів, це повернуло б ту саму синхронізацію кількох джерел; (2) лишити як є — відкинули через дублювання форматів, яке з часом не зникає, а розходиться.
**Реалізація:** #60.

### Уточнення: `.claude/` читає лише Claude Code

**Виправляє:** запис вище.
**Рішення:** твердження, що скіли й хуки — «один механізм, який усі три інструменти читають із `.claude/`», **фактично неправильне**. `.claude/skills/` і `.claude/hooks/` читає лише Claude Code.
**Чому:** підняв CodeRabbit на PR #61, вказавши на пряму суперечність із `CONTRIBUTING.md`, який від початку визначав ці файли як Claude Code only. Помилка була не в наслідку, а в обґрунтуванні: ним виправдовувалась відмова від glob-based розбиття. Сама відмова лишається чинною (різні механізми глобів повернули б синхронізацію кількох джерел), а аргумент «усі три читають `.claude/`» — ні.
**Наслідок:** після розділення інструменти, що читають лише `AGENTS.md`, втратили task workflow, PR workflow і документаційні тригери. Тобто розділення тихо погіршило їх, а не лишило нейтральними — це й привело до наступного рішення.

### Claude Code як єдиний підтримуваний інструмент

**Рішення:** `.cursor/rules/`, `.agents/rules/` і `.cursorrules` видалені. Проєкт офіційно розробляється в Claude Code. `AGENTS.md` і `CONTRIBUTING.md` прямо кажуть, що інший інструмент, який читає `AGENTS.md`, отримує все, що формує код, і **не** отримує ситуативний workflow.
**Чому:** після переносу ситуативних правил у `.claude/` конфіги Cursor і Antigravity стали обіцяти повний набір правил, а віддавати неповний: вони імпортували `AGENTS.md`, який тепер посилається на скіли, недоступні цим інструментам. Напівживий конфіг гірший за його відсутність — він виглядає підтримуваним і мовчки дає іншу поведінку агента.
**Компроміс:** повернення до Cursor чи Antigravity потребуватиме заведення конфігу наново. Краще зібрати його під конкретний інструмент із поточного `AGENTS.md`, ніж роками підтримувати файл, у який ніхто не заходить і чию актуальність ніхто не перевіряє — саме такі файли розходяться першими, що вже сталось із витяжками в `.cursor/rules`.
**Альтернатива яку відкинули:** повернути повний нормативний текст у `AGENTS.md`, лишивши скіли й хуки покажчиками на нього (пропозиція CodeRabbit). Відкинули: дублювання нормативного тексту в двох місцях і було проблемою, яку розвʼязував #60.
**Реалізація:** #60 (PR #61).

### Відповідь на коментар CodeRabbit — за винятком, не за замовчуванням

**Звужує:** правило в `AGENTS.md`.
**Рішення:** письмова відповідь потрібна не на **кожен** коментар, а в трьох випадках: не згоден із зауваженням; виправив інакше, ніж запропоновано; з діфа не видно причини виправлення. Дослівне виправлення за пропозицією відповіді не потребує — діф і повідомлення коміту вже є записом.

**Чому:** попереднє формулювання писалось до того, як зʼявились спостереження за реальною поведінкою CodeRabbit. Перевірено через GitHub API на PR #59: усі девʼять тредів закрив **сам бот**, без жодного ручного resolve — сім після інкрементального рев'ю нового коміту, два після заперечень, які він явно відкликав. Відповіді на заперечення прийшли за 18 і 20 секунд, тобто діалог у треді працює незалежно від того, чи завершився повний прохід рев'ю. За таких умов «fixed» на механічне зауваження не додає нічого до діфа й розбавляє ті відповіді, що справді несуть аргумент.

**Компроміс:** зникає гарантія, що кожен тред має слід нашого міркування. Межа «з діфа не видно причини» суб'єктивна, і спокуса не писати сильніша за спокусу написати; при сумніві правило вимагає писати.

**Наслідок:** нове формулювання збігається з `CONTRIBUTING.md` («fix it **or** leave a comment explaining why not»), який весь час казав саме це — тобто звуження прибирає стару розбіжність, а не створює нову.

**Що спричинило перегляд:** на тому ж PR відповіді написані на 2 із 9 коментарів, і найдорожчим пропуском виявився не механічний фікс, а зауваження, яке виправили **інакше** ніж просили: тред закрився автоматично, і причина вибору ніде не лишилась.

### Маркери відповідності коду в `API-CONVENTIONS.md`

**Рішення:** кожна нумерована секція `docs/API-CONVENTIONS.md` відкривається маркером (`✅ holds`, `✅ holds, vacuously`, `🔧 debt #NN`); підсекція має власний, якщо розходиться з батьківською. Маркер відповідає на одне питання: **чи задовольняє наявний код це правило**. Обов'язковості правила він не зачіпає — `🔧` означає «обов'язкове для нового коду, але вчити його з кодової бази не можна». Легенда і правило перевертання живуть тільки в `API-CONVENTIONS.md`; цей запис і PR-шаблон посилаються туди, а не переказують.

**Чому:** файл описував у теперішньому часі механізми, яких немає. §4 казала, що помилки ловить глобальний хендлер, — тобто **інструктувала не писати** власний захист, спираючись на неіснуючий `app.onError`. §5 і §8 відсилали по готову реалізацію в `src/lib/`, де її нема. §7 і §9 гірші: там код не відстає, а робить протилежне — `transactions.date` оголошена `timestamp`, а `DELETE /accounts/:id` знищує історію транзакцій каскадом, рівно те, що §9 забороняє. Читач діставав дві суперечливі відповіді — документ і код — без підказки, яка авторитетна.

**Компроміс:** маркер треба перевертати, коли закривається **остання** з названих ним issue. Без тригера він згниє, і тоді `✅` буде гіршим за початковий стан, бо читається як перевірене твердження. Тому тригер механічний: `scripts/check-conformance-markers.mjs` окремим job'ом валить збірку на закритій чи неіснуючій issue і на нумерованій секції без маркера. Хук тут не годиться принципово — `PostToolUse` реагує на правку файлу, а не на закриття issue.

**Чого автоматизувати не вдасться:** зворотний напрямок, `✅` → `🔧`: жодна статична перевірка не знає, що новий роут-модуль порушив §2. Звідси два стильові правила для обґрунтувань при `✅` — вони не мають ламатись від звичайного фічового PR («today that is `accounts.ts` alone», а не «no other route module exists yet»), і не мають посилатись на номери рядків, бо вставлений вище тест зсуває їх мовчки.

**Альтернатива яку відкинули:** тримати нереалізовані секції тут, а в `API-CONVENTIONS.md` лишити тільки реальність. Відкинули: цінність цих секцій саме в тому, що їх читають **до** написання коду, а тут — наратив, у якому не шукають форму поля.

**Реалізація:** #71 (маркери), #73 (перевірка в CI).

### Уточнення: неперевернутий маркер не червонить PR, лише наступний `main`

**Уточнює:** «Маркери відповідності коду в `API-CONVENTIONS.md`» вище.
**Рішення:** «документаційний PR дізнається про протухлий маркер за секунди» — вірно для решти режимів відмови, але не для того, заради якого перевірку заводили: неперевернутий маркер до мерджу не видно. Єдине джерело цього правила — легенда «Conformance markers» у `docs/API-CONVENTIONS.md`.
**Чому:** `Closes #NN` закриває issue в момент **мерджу**, тож поки PR відкритий, номер ще відкритий і джоба зелена — незалежно від того, перевернули маркер чи ні. Пропущене перевертання таки спливає, а не лежить у файлі роками, але «спливає» і «не пройде» — різні гарантії, і слабшу з них той запис описував як сильнішу.
**Компроміс:** сигнал приходить постфактум — червоний прогін на захищеній гілці замість заблокованого PR. Альтернатива вимагає знати стан issue до мерджу, чого GitHub не дає в принципі.
**Альтернатива яку відкинули:** зробити джобу required status check. Саме на цьому режимі відмови вона до мерджу зелена, тож обов'язковість його не спіймає; на решті режимів джоба й так червона. Заміна нетехнічна — чекбокс у `.github/pull_request_template.md`.
**Реалізація:** знайдено при рев'ю PR #78; правка суто текстова, окремої issue немає.

### `scripts/` — plain JavaScript під `checkJs`, свідомий виняток із «TypeScript, no exceptions»

**Рішення:** інструментальні скрипти репозиторію (`scripts/*.mjs`) пишуться звичайним ESM JavaScript із JSDoc, а не TypeScript. Типізація з них **не** знімається: `tsconfig.scripts.json` (`allowJs` + `checkJs` + той самий `strict`) тримає JSDoc під тими самими правилами, а `npm run typecheck` виконує обидва конфіги. ESLint покриває каталог окремим блоком із node-глобалами, як уже зроблено для `.claude/hooks/*.cjs`.
**Чому:** job `markers` має відповідати за секунди й не залежати від `npm ci`, тому він не ставить залежності взагалі. Скрипт на TypeScript потребував би або кроку збірки, або `tsx` — тобто `npm ci` перед кожною перевіркою документа. Прецедент уже є: `.claude/hooks/doc-rules.cjs` з тих самих причин звичайний JS.
**Компроміс:** це виняток із «TypeScript, no exceptions» у `AGENTS.md`. Приймаємо вузько — тільки `scripts/` і `.claude/hooks/`, тільки для коду поза застосунком, і тільки за умови `checkJs`. Без цієї умови це був би просто нетипізований код; із нею різниця лише в синтаксисі анотацій. Ціна: два tsconfig, які мусять лишатись сумісними, тому другий `extends` перший і перевизначає рівно чотири опції.
**Що це дало одразу:** `checkJs` на першому ж прогоні знайшов три незахищені `Map.get()` і `unknown` у `catch`, які ESLint пропустив.
**Альтернатива яку відкинули:** (1) TypeScript через `tsx` — повертає `npm ci` у job, заради якого його й виносили; (2) лишити `scripts/` поза перевіркою типів — тоді єдиною статичною перевіркою, здатною завалити CI, лишався б `no-undef`.
**Реалізація:** #73.

### Флоу розбору рев'ю — три скіли замість одного

**Рішення:** розбір зауважень рев'ю розділений на два виклики. Перший — `discuss-comments` (знахідки `/code-review`) або `discuss-rabbit` (коментарі CodeRabbit): проходить по одному, ухвалює fix-or-skip разом із розробником, лишає тріажований план. Другий — `implement-comments`: застосовує ухвалене в тій формі, в якій ухвалено. Перший етап іде на `opus` і має `disallowed-tools: Edit Write NotebookEdit`, другий — на `sonnet`. Усі три несуть `disable-model-invocation: true`, тобто викликає їх людина, не модель. Нормативний текст живе в самих скілах; тут — лише компроміси.

**Чому два виклики, а не один скіл:** між ними потрібен чекпоінт, на якому розробник схвалює тріажований план **до** того, як зміниться перший рядок коду. Другий мотив — ціна: відокремлене виконання можна віддати слабшій моделі.

**Чому правки заблоковані на етапі тріажу:** три самостійні причини. (1) Без блокування модель зсовується у виправлення посеред обговорення, і чекпоінт тихо зникає. (2) План — єдиний артефакт етапу, тож рішення можна відкотити, не відкочуючи код. (3) Правки з'їдають контекст, потрібний, щоб тримати всі знахідки в голові одночасно.

**Чому різні моделі:** судження fix-or-skip — найдорожча помилка в циклі, і механізм проти неї слабкий. `discuss-comments` вимагає, щоб відкладена робота ставала новим пунктом у `docs/PROGRESS.md`, але це спрацьовує лише коли skip розпізнали як відкладену роботу — а хибний skip це рівно той, який таким не визнали. Застосування вже ухваленого такої вимоги не має. **Це ставка, а не вимір:** немає прогону, який показав би, що `sonnet` справляється із застосуванням і не справляється з тріажем. Момент для перевірки — коли `implement-comments` уперше зробить не те, що було ухвалено.

**Чому два фронтенди, а не один:** їх розділяє все три. Джерело даних — CodeRabbit тягнеться через GitHub GraphQL із тредами й пагінацією, `/code-review` віддає знахідки прямо в сесію. Правило відповіді — у CodeRabbit є треди, куди заперечення треба постити негайно, у локального рев'ю такого етапу немає. Момент виклику — один до пушу, другий після.

**Компроміс:** три файли розходяться між собою рівно так, як у цьому проєкті вже розходились копії правил. Спільна частина винесена в `implement-comments` саме тому; решта дублювання лишається ризиком.

**Реалізація:** приїхало всередині PR #70 (мультивалютність), без власної issue — всупереч `task-workflow`, який вимагає окрему issue для наскрізної роботи. Задокументовано заднім числом у #76.

### Перевірка посилань у тексті хука — тест, а не CI-джоба

**Рішення:** `.claude/hooks/doc-rules.test.mjs` покриває хук із двох боків. Перший — посилання: бере рядки нагадувань із `doc-rules.cjs`, витягує з них шляхи до файлів і назви npm-скриптів, і падає, якщо хоч одне не існує. Другий — поведінка: запускає хук так само, як його запускає Claude Code (JSON на stdin), і перевіряє, що він озивається на правках схеми та створенні роут-модуля, мовчить на всьому іншому, віддає саме `hookSpecificOutput`, а не звичайний текст, і завжди виходить із кодом 0. Звичайний тест у наявному наборі — без окремої джоби в CI й без токена.

**Чому не за зразком #73:** маркери `🔧 debt #NN` мають власну джобу, бо їхнє твердження стосується **зовнішнього** стану — чи відкрита issue на GitHub. Тут усе, що згадує хук, лежить у цьому ж репозиторії, тож мережа, токен і джоба були б платою ні за що.

**Що ловить:** «названо те, чого немає». Рівно цей клас пропустив рядок про Mermaid ERD, який прожив від першого коміту хука до #76: eslint бачив коректний рядковий літерал, `npm test` перевіряв застосунок, а запуск хука доводив лише те, що він друкує, — не те, що надруковане правдиве.

**Чого не ловить:** «названо існуюче, але порада хибна» — посилання на секцію «Stack» замість «Data model» лишилось би зеленим. Заголовки секцій свідомо поза перевіркою: відрізнити заголовок від будь-якої іншої фрази в лапках можна лише перебудувавши текст хука на дані, а ціна цього — читабельність самого хука, чия цінність саме в тому, що нагадування видно очима.

**Реалізація:** #76. При мерджі з `main` виявилось, що тест не потрапляв у жоден `include` Vitest і мовчки зникав із `npm test`, лишаючись зеленим при прямому запуску, — звідси третій проєкт `hooks` (див. «Уточнення: проєктів Vitest три, а не два»).

### Редакція документації: append-only знято, зміст генерується

**Рішення:** записи цього файлу можна редагувати — правило «записи не переписуються, тільки додаються нові» скасоване. Натомість зафіксовано два обмеження. Перше: запис тримається шести оголошених полів, а перехресні посилання живуть у полях `**Уточнює:**` / `**Виправляє:**` / `**Оновлює:**` / `**Звужує:**` / `**Виконує:**` і в `**Виправлено:**` на застарілому записі — не в заголовку. Друге: зміст генерує `scripts/generate-toc.mjs`, а `npm run check:toc` у job'і `config-paths` валить збірку, коли він застарів.

**Чому:** вимір показав, що 54% файлу — секції Tooling і CI, тобто проєкт документував власний тулінг докладніше за свій домен, заради якого існує. Доменні записи трималися шести полів і вкладались у 2–4 рядки; мета-записи винайшли 29 разових полів, кожне вжите рівно один раз, і виросли до 620 слів. Append-only при цьому мав власну ціну для навчального файлу: 13 із 53 записів виправляють попередній, тож читач, який шукав формулу балансу, першою зустрічав редакцію, яку наступний запис уже спростував.

**Компроміс:** зникає гарантія, що текст запису дослівно збігається з тим, яким його ухвалили, — журнал перестає бути аудитом. Ланцюжок рішень зберігається (виправлення лишаються окремими записами, а не зливаються в один), але довести, якими словами це формулювалось у липні, тепер можна лише через `git log`. Приймаємо: цей файл читає одна людина, щоб вчитися, а не сторона, якій треба доводити незмінність.

**Чому зміст саме генерується:** індекс на 50+ записів, який підтримують уручну, — та сама заявка, що й `path:` на теку, якої немає: читається як правда довго після того, як став неправдою, і жоден сигнал про це не повідомляє. Заразом генератор — єдине місце, звідки ланцюжки уточнень видно списком.

**Альтернатива яку відкинули:** лишити наявні записи недоторканими й застосувати ліміт лише до нових. Обсяг тоді не зменшується взагалі, а 54% мета-документації — це вже наявний стан, а не тенденція.

**Наслідок:** `generate-toc.mjs` — третій скрипт перевірки, тобто настав тригер на витяг спільного коду в `scripts/lib/`, який назвав запис «Перевірка шляхів у конфігах тулінгу». Виконано в записі нижче.

### Перевірка поверхні CI: `ci.yml` проти прози, що його описує

**Виконує:** відкритий пункт `docs/PROGRESS.md` «Зробити перелік джоб CI перевірюваним».
**Рішення:** `check-config-paths.mjs` отримав шостий інваріант. Він читає `.github/workflows/ci.yml` і валить збірку, коли: джоба не згадана в `CONTRIBUTING.md`; перевірка `check:*`, яку CI запускає, не названа в `CONTRIBUTING.md`, PR-шаблоні чи котромусь README; перевірка названа в прозі, але в CI не запускається; `npm run` кличе скрипт, якого немає в `package.json`. Плюс той самий гейт «розібрано нуль — значить читач розійшовся з файлом», що й у решті цього скрипта.

**Чому саме `check:*`, а не всі скрипти:** `typecheck`, `lint` і `test` описані гуртом («all three»), а не поіменно, тож вимога згадати кожен окремо червонила б прозу, яка й так правильна. Сімейство `check:*` — те, яке документи перелічують по одному, і те, яке вже двічі розійшлося.

**Які документи в гейті — правило, не список:** ті, що **інструктують** запускати перевірки, тобто `CONTRIBUTING.md` і PR-шаблон. README звідти прибрані разом із самим переліком команд: README — огляд, і його рівень — «CI звіряє документацію з кодом», а не назви скриптів. `ONBOARDING.md` поза гейтом, хоч і називає всі три: він описує локальний запуск, а не склад CI, тож гейт доповідав би цю різницю як помилку.

**«Називає» — це окремий код-спан, а не збіг символів.** Правило перевірялось тричі, і перші два не витримали на одному й тому ж імені. `includes('ci')` знаходило `ci` всередині слова decisions — тобто головна джоба репозиторію не могла бути визнана недокументованою **ніколи**. Звуження до «в бектиках і на межах токена» теж пройшло: `` `.github/workflows/ci.yml` `` і `` `npm ci` `` містять `ci`, обмежене пунктуацією. Чинне правило точне: спан дорівнює імені або дорівнює команді, що його запускає. Заразом довелось прибирати огорожі коду перед розбором — потрійні бектики розсинхронізовували пари, і на `CONTRIBUTING.md` це ховало **всі** справжні спани після першої огорожі.

**Що з цього випливає ширше:** зіставляти прозу з кодом по підрядку не можна, якщо ім'я — коротке або звичайне слово. Проксі «чи згадано» здавався дешевим і був неправильний в обидва боки одразу: занадто слабкий (збіги) і занадто сильний (вимагав переліку в чотирьох файлах). Тест це не спіймав, бо перевіряв ім'я `brand-new`, достатньо характерне, щоб дірку обійти, — правило, перевірене лише на легкій половині, засвідчує гарантію, якої код не дає.

**Документ розбирається один раз, обидва напрями читають той самий набір.** Спершу кожна перевірка тримала власний текст і власну регулярку, і вони розійшлися вдруге: прямий напрям навчився пропускати огорожі коду, зворотний лишився сканувати сирий текст — і документ, який цитує **власне повідомлення про помилку**, отримував червону збірку за цілком правильну прозу. `documentNames()` розбирає документ у набір названих спанів один раз; звідти читають і прямий напрям, і зворотний. Це не оптимізація (файл на 5 КБ, шість розборів замість одного) — це те, що робить розходження двох напрямів **непредставним**, а не виправленим. Заразом непарна кількість огорож стала окремою проблемою: читач, який мовчки оглядає половину документа, гірший за той, що зупиняється.

**Джоби звіряються лише в один бік — свідомо.** Для скриптів працюють обидва, бо `check:` — простір імен: названий скрипт, якого CI не запускає, ні з чим не сплутати. Ім'я джоби — звичайне слово, і спан `` `markers` ``, що описує прибрану джобу, нічим не відрізняється від того самого слова в прозі. Обидва обхідні шляхи відкинуто: евристика «схоже на kebab-case» ловила б `pull_request` і `config-paths` у будь-якому контексті, а розбір саме булітів секції Testing прив'язав би перевірку до верстки тексту — тобто документ почав би обслуговувати чекер. Залишковий ризик вузький: разом із джобою зазвичай зникає її `check:*`-скрипт, а це зворотна перевірка ловить. Непокрито лише «прибрали джобу, яка не запускає жодного `check:*`».

**Що це знайшло одразу:** додавання `check:toc` лишило його неназваним у PR-шаблоні й **обох** README. Рев'ю знайшло одне з трьох; інваріант — усі три, на першому ж прогоні.

**Компроміс:** читач `ci.yml` рядковий, як і читач `.coderabbit.yaml`, і з тієї ж причини — джоба має відповідати без `npm ci`. Workflow у flow-стилі він прочитає порожнім, тому «нуль джоб» трактується як провал. Ціна та сама: при зміні форми конфігу треба чіпати й читач.

**Заразом:** спільне для трьох скриптів винесено в `scripts/lib/report.mjs` — спрацював тригер «третій скрипт». Винесено лише байт-у-байт однакове (`formatCause`, `markFailed`); три `report` лишились на місці, бо розходяться текстом і сигнатурою — рівно як передбачав запис, що цей тригер поставив.

## База даних — загальна структура

### Foreign keys (id), не текстові поля для зв'язків

**Рішення:** `account_id`, `category_id` в `transactions` — integer/uuid посилання, не назви текстом.
**Чому:** зв'язки через id дають цілісність даних (перейменування категорії не ламає історію), швидкий підрахунок (`SUM`/`GROUP BY`), захист від видалення пов'язаних даних через foreign key constraints.

### Баланс рахунку рахується динамічно, не зберігається в `accounts`

**Виправлено:** формула нижче неточна — чинна редакція в «Уточнення: формула балансу і знак суми».
**Рішення:** немає поля `balance` в `accounts`. Баланс = `SUM` транзакцій по `account_id`.
**Чому:** уникаємо race conditions при паралельних записах — дві одночасні транзакції можуть перезаписати результат одна одної якщо баланс зберігається окремим полем. Джерело правди — самі транзакції.
**Компроміс:** повільніше при дуже великих обсягах даних — вирішується індексом на `account_id`; за потреби пізніше можна кешувати в Redis.
**Альтернатива яку відкинули:** зберігати `balance` і оновлювати через `SELECT FOR UPDATE` в транзакції — швидше читання, але вищий ризик тихих багів якщо десь забути обгорнути оновлення в транзакцію.

### `category_id` в `transactions` — nullable, `onDelete: set null`

**Рішення:** якщо категорію видалено — транзакція лишається з `category_id = null` ("без категорії"), не видаляється каскадно.
**Чому:** видалення категорії не повинно видаляти історію транзакцій.
**Альтернатива яку відкинули:** системна категорія "Інше" створена автоматично для кожного юзера — бізнес-логічно чистіше, але додає складність (seed-логіка при реєстрації, захист від видалення) не потрібну для MVP.

### `category_id` в `budgets` — required, `onDelete: cascade`

**Рішення:** якщо категорію видалено — пов'язані записи `budgets` видаляються каскадно через `budgets.category_id`.
**Чому:** бюджет без категорії втрачає сенс для планування, на відміну від історичної транзакції.
**Компроміс:** видалення категорії також прибирає її бюджетні ліміти; якщо потрібна історія бюджетів, її треба буде моделювати окремо.

### Cascade delete від `users` до всіх дочірніх таблиць

**Рішення:** видалення юзера каскадно видаляє його `accounts`, `categories`, `transactions`, `budgets`.
**Чому:** дані без власника не мають сенсу існувати в системі.

### Індекси на всіх foreign key колонках

**Рішення:** індекси на `user_id`, `account_id`, `category_id` у всіх таблицях де вони присутні.
**Чому:** без індексу — full table scan при кожному запиті "дані цього юзера" і при JOIN між таблицями. Знайдено CodeRabbit на першому review, виправлено окремою міграцією.

### UUID замість `serial` для всіх primary keys

**Рішення:** всі `id` — `uuid('id').primaryKey().defaultRandom()`, не `serial`.
**Чому:** `serial` розкриває кількість записів (enumeration attack), ускладнює мердж даних з кількох джерел, не можна згенерувати id до запису в базу. Плюс консистентність з Better Auth, який вже використовує текстові/uuid id.
**Коли прийнято:** до появи реальних даних в таблицях — зміна типу primary key після появи даних значно дорожча (треба одночасно конвертувати всі foreign keys).

### `numeric(12, 2)` для всіх грошових полів

**Рішення:** `amount` в `transactions` і `budgets` — `numeric({ precision: 12, scale: 2 })`, не `float`.
**Чому:** `float` має похибку округлення (0.1 + 0.2 ≠ 0.3) — неприпустимо для фінансових розрахунків.

### Мультивалютність: `char(3)` ISO-4217, агрегати завжди з `GROUP BY currency`

**Рішення:** `accounts.currency` — `char(3)` з `CHECK` на формат і спільною Zod-схемою (обмежений enum ISO-4217), не `varchar(10)` з довільним рядком. `budgets` отримує власне обовʼязкове поле `currency`. `transactions` власної валюти **не має** — вона успадковується від рахунку. Будь-який агрегат, що сумує гроші більш ніж по одному рахунку, групується по валюті й ніколи не змішує.
**Чому:** ревізія показала, що `z.string().min(1).max(10)` приймає `"$$$"`, `"гривня"` і `"usd"` як три різні валідні валюти, а `budgets` не мав валюти взагалі — бюджет «5000» у користувача з карткою UAH і депозитом USD не означає нічого. Це найдорожчий різновид помилки: `SUM` по різних валютах повертає число, яке виглядає правильним, і ніщо ніде не падає.
**Компроміс:** витрати з рахунку в іншій валюті не потрапляють у бюджет цієї категорії. Тобто бюджет «Продукти 5000 UAH» ігнорує продукти, куплені з USD-рахунку. Це свідомо: конвертація без курсів бреше тихіше, але так само.
**Альтернатива яку відкинули:** одна базова валюта на користувача (`users.base_currency`), рахунки без власної валюти. Простіше — звіти без жодного `GROUP BY` — але не відповідає реальності користувача цього трекера (картка UAH + депозит USD одночасно), і повернення мультивалютності пізніше коштувало б міграції з реальними даними.
**Реалізація:** #36. Рішення прийняте під час ревізії беклогу 2026-08-01, до написання коду транзакцій — саме щоб #15 і #18 не писались поверх невизначеності.

### Уточнення: формула балансу і знак суми

**Виправляє:** «Баланс рахунку рахується динамічно» вище.
**Рішення:** `amount` завжди додатний — `CHECK (amount > 0)` в базі і `.positive()` в Zod; напрям руху грошей виводиться **виключно** з `type`. Канонічна формула балансу: `SUM(CASE WHEN type = 'income' THEN amount ELSE -amount END)`, одна реалізація в `src/lib/`.
**Чому:** формулювання «Баланс = `SUM` транзакцій по `account_id`» неточне. З `type: income|expense` і беззнаковим `amount` буквальний `SUM(amount)` дає **оборот**, не баланс. Помилка вже встигла поширитись — issue #15 скопіював це формулювання дослівно. Конвенції знака при цьому не існувало взагалі: ніщо не заважало записати `-500` з `type = 'expense'`, і воно б **додалось** до балансу.
**Компроміс:** формула складніша за простий `SUM`, і її не можна повторювати по хендлерах — тільки одна реалізація, інакше розійдеться.
**Альтернатива яку відкинули:** (1) знакова сума з похідним `type` — простіший `SUM(amount)`, але ніщо не ловить дохід, записаний з мінусом, і помилку видно тільки очима на код-рев'ю. (2) Подвійний запис (double-entry, debit/credit) — найправильніше з бухгалтерського боку, баланс сходиться за побудовою, перекази моделюються природно; відкинули як надмірний обсяг для MVP — це переписування схеми `transactions` і всіх тікетів #15–#17.
**Реалізація:** #37.

### `timestamptz` для `created_at`, `date` для `transactions.date`

**Рішення:** усі `created_at`/`updated_at`/`archived_at` доменних таблиць — `timestamptz`. `transactions.date` — тип `date` (календарна дата без часу і без таймзони), у JSON `YYYY-MM-DD`. Таблиці `auth_*` не чіпаємо — ними керує Better Auth, зміна типів зламає адаптер.
**Чому:** у первинній міграції всі часові колонки — `timestamp` без таймзони. Той самий момент зберігається як різні значення на машині розробника (UTC+3) і в контейнері на Railway (UTC), тому межі місяця у звітах поїдуть залежно від того, де крутиться процес. Окремо для `transactions.date`: транзакція має календарну дату, а не момент — «витратив 200 пʼятого липня». Зберігання її як timestamp робить звіт «за липень» залежним від часу доби й таймзони.
**Коли прийнято:** до появи реальних даних у таблицях — та сама логіка, за якою вже перейшли на UUID (запис вище). Зараз це зміна типу на порожній базі; після продакшену — міграція з конвертацією і ризиком тихого зсуву дат.
**Компроміс:** банківська інтеграція (Фаза 2) віддає реальні timestamps — для точного моменту доведеться додати окреме поле `occurred_at timestamptz` поруч із календарним `date`, а не переписувати тип.
**Альтернатива яку відкинули:** `timestamptz` для `transactions.date` плюс `users.timezone`, і всі звіти через `AT TIME ZONE`. Гнучкіше і одразу готове до банківської синхронізації, але ускладнює кожен звітний запит і вимагає звідкись узяти таймзону користувача — складність під фічу, якої ніхто не просив.
**Реалізація:** #38.

### Видалення рахунку — soft delete через `archived_at`, не каскад

**Рішення:** `DELETE /accounts/:id` виставляє `archived_at`, рядок лишається. `transactions.account_id` переводиться з `onDelete: cascade` на `onDelete: restrict` — щоб hard delete став неможливим на рівні бази, а не лише за домовленістю. `GET /accounts` показує тільки неархівовані; `GET /accounts/:id` віддає й архівований, щоб історія транзакцій мала на що посилатись. Нові транзакції на архівований рахунок — 422.
**Чому:** `transactions.accountId` мав `onDelete: cascade`, а `DELETE /accounts/:id` уже працював у змердженому коді — тобто видалення рахунку **тихо стирало всю історію транзакцій**. Це прямо суперечить рішенню «`category_id` в `transactions` — nullable, `onDelete: set null`» вище, де аргумент був саме «видалення категорії не повинно видаляти історію транзакцій». Для рахунку той самий аргумент сильніший: закритий депозит не означає, що торішніх витрат не було. Каскад `transactions → accounts` ніколи не обговорювався — він успадкувався за замовчуванням і не мав тут запису взагалі.
**Компроміс:** кожен list-запит по рахунках зобовʼязаний фільтрувати `archived_at IS NULL`, і забути цей фільтр — новий клас помилки, якого раніше не існувало. UNIQUE на назву рахунку теж стає partial (`WHERE archived_at IS NULL`), інакше архівований рахунок блокував би створення нового з тією ж назвою.
**Альтернатива яку відкинули:** `RESTRICT` без `archived_at` — заборонити видалення, поки є транзакції (422), і вимагати спершу їх прибрати. Простіше, без нового поля й без ризику забути фільтр, але залишає користувача з рахунком, який неможливо приховати зі списку, не знищивши історію.
**Реалізація:** #39.

### Бюджети — явні екземпляри з `period_start`, не безстрокові правила

**Рішення:** `budgets.period_start date NOT NULL` + `UNIQUE (user_id, category_id, period, period_start)`. `CHECK`, що `period_start` узгоджений з `period`: 1-ше число місяця для `monthly`, понеділок для `weekly`. Бюджет на новий період створюється явно.
**Чому:** `period: monthly|weekly` без жодного якоря в часі не дозволяє відповісти на базові питання: який бюджет був у червні, що сталося, коли в липні ліміт підняли з 5000 до 7000, і від якої дати рахувати виконання. Без `UNIQUE` можна було створити пʼять «monthly» бюджетів на ту саму категорію, і жоден агрегат не знав би, який справжній. Порівняння плану з фактом — головна причина існування бюджетів — без цього некоректне в принципі.
**Компроміс:** бюджет на наступний місяць треба створити вручну; автоматичне перенесення потребує фонової задачі (BullMQ — Фаза 2).
**Альтернатива яку відкинули:** (1) бюджет як безстрокове правило, прогрес завжди за поточний календарний період — найпростіше, але історії бюджетів не існує: піднявши ліміт, ти заднім числом змінюєш оцінку всіх минулих місяців. (2) Довільний діапазон `start_date` + `end_date` замість enum — максимально гнучко (відпустка, проєкт), але зʼявляється цілий клас проблем із перетинами діапазонів і простий `UNIQUE` стає неможливим.
**Реалізація:** #40.

### Переказ між власними рахунками — два звʼязані рядки з `transfer_group_id`

**Рішення:** переказ — це **два** рядки в `transactions` зі спільним `transfer_group_id`: `expense` на рахунку-джерелі й `income` на рахунку-отримувачі, обидва з `category_id = null`, вставляються в одному `db.transaction()`. Усі звіти по доходах і витратах виключають рядки з `transfer_group_id IS NOT NULL`. Обидва рахунки мають належати одному користувачу, бути в одній валюті й не бути архівованими — інакше 422.
**Чому:** без окремої моделі переказу переміщення 10 000 з картки на депозит записується як витрата плюс дохід, і звіт показує «витратив 10 000», хоча гроші нікуди не поділись — аналітика бреше саме на найбільших сумах. Два рядки обрані тому, що формула балансу при цьому не змінюється взагалі: витрата вже лежить на джерелі, дохід — на отримувачі, і `SUM(CASE ...)` обробляє це без жодного спецвипадку.
**Компроміс:** одна логічна операція займає два рядки, тому редагування переказу мусить чіпати обидва атомарно — тому `PATCH`/`DELETE` окремого рядка переказу через `/transactions/:id` заборонені (422), редагувати можна лише переказ цілком.
**Альтернатива яку відкинули:** один рядок із `type = 'transfer'` і nullable `to_account_id`. Менше рядків і простіше редагування, але кожен запит балансу мусив би шукати `WHERE account_id = X OR to_account_id = X`, а `CHECK`-обмеження ускладнюються (`to_account_id` обовʼязковий лише для одного значення `type`) — складність переїжджає з запису в кожне подальше читання.
**Побічна користь:** це перше й поки єдине місце в проєкті, де транзакція бази даних справді потрібна — вимога `AGENTS.md` «use transactions when modifying multiple tables» досі не мала жодного застосування.
**Реалізація:** #42.

## Автентифікація

### Better Auth з окремими `auth_*` таблицями

**Рішення:** таблиці Better Auth (`auth_user`, `auth_session`, `auth_account`, `auth_verification`) окремо від таблиці `users` (доменний профіль фінтрекера).
**Чому:** уникнути конфлікту назв (`accounts` фінансові рахунки vs `auth_account` OAuth-акаунти в базі Better Auth) і розділити відповідальність — Better Auth керує автентифікацією, `users` — доменними даними.

### Зв'язок `users.auth_user_id → auth_user.id`, one-to-one

**Рішення:** `users` має `authUserId` (unique, FK на `auth_user.id`, cascade delete).
**Чому:** один обліковий запис Better Auth відповідає рівно одному фінансовому профілю.

### Сесія через HttpOnly cookie, не JSON токен в тілі відповіді

**Рішення:** Better Auth сесія через HttpOnly cookie, не токен що зберігається на клієнті в localStorage.
**Чому:** JavaScript не може прочитати HttpOnly cookie навіть при XSS-атаці — безпечніше ніж зберігання токена в localStorage/sessionStorage.

### Створення запису в `users` — через hook, не окремий endpoint

**Виправлено:** «hook атомарний» нижче — неправда; чинна редакція в «Уточнення: hook не атомарний з `auth_user`».
**Рішення:** `onUserCreate` hook в Better Auth автоматично створює запис в `users` одразу при реєстрації. Окремий endpoint (напр. `/api/profile/setup`) — опціонально, для локальної зручності, не є критичним шляхом.
**Чому:** hook атомарний і надійний — неможливо "забути" викликати його з клієнта; уникає розсинхронізації коли є `auth_user` без відповідного профілю в `users`.

### Реєстрація напряму через `/api/auth/sign-up/email`, без кастомної обгортки

**Рішення:** реєстрація йде через змонтований Better Auth handler (`app.on(['POST','GET'], '/api/auth/*', ...)` в `src/index.ts`) і його власний ендпоінт `POST /api/auth/sign-up/email` — без кастомного `/api/auth/register`. `emailAndPassword.autoSignIn` встановлено в `false` (`src/lib/auth.ts`).
**Чому:** дефолтна поведінка Better Auth для вже зареєстрованого email — `422`, що збігається зі статус-кодами проєкту з `AGENTS.md` (`400/401/403/404/422/500` — 409 там немає) без жодної кастомної обгортки. `autoSignIn: false` додатково закриває email-enumeration: без цього sign-up для вже зареєстрованого email повертає відмінну від успіху відповідь (422), дозволяючи зловмиснику перевіряти, які email вже зареєстровані в системі. Перевірено наживо: другий sign-up з тим самим email не створює другий рядок в `auth_user` (Better Auth повертає синтетичний, неперсистований об'єкт з тим самим 200 і формою відповіді).
**Компроміс:** `/api/auth/sign-up/email` стилістично не збігається з плоским REST-стилем решти API (`/accounts`, `/categories`). Після реєстрації користувач більше не отримує сесію автоматично (`token: null` у відповіді) — логін стає обов'язковим окремим кроком, а не опціональною зручністю.
**Альтернатива яку відкинули:** кастомний `POST /api/auth/register` з власними 201/409, що обгортає `auth.api.signUpEmail()` — відкинули, бо довелось би вручну підтримувати ще один шар поверх Better Auth без реальної користі, а 409 не входить у статус-коди проєкту взагалі. Також відкинули `requireEmailVerification: true` як механізм anti-enumeration — теж working, але вимагає реалізованої `sendVerificationEmail` (реальний email-провайдер), якого зараз немає в проєкті; лишається кандидатом на окрему майбутню фічу "email verification".

### Rate limiting: явний `customRules`, in-memory storage

**Рішення:** `rateLimit.enabled: true` + `customRules` для `/sign-up/email` (60с/10) і `/sign-in/email` (60с/5) — суворіше за глобальний дефолт (60с/100). Storage — `memory` (дефолт Better Auth), не Redis.
**Чому:** CodeRabbit review на PR #27 підняв, що `AGENTS.md` вимагає rate limit на auth endpoints, а конфіг його не задавав явно. Better Auth сам вмикає rate limiting за замовчуванням, але лише в production і з одним глобальним лімітом, не заточеним під auth конкретно. Явний `customRules` не додає нової залежності і працює однаково в dev/prod.
**Компроміс:** in-memory storage не координується між репліками — при горизонтальному масштабуванні кожна репліка рахує ліміт окремо, ефективний ліміт множиться на кількість реплік. Прийнятно зараз (один інстанс, Railway/Render), недостатньо, якщо з'являться кілька реплік.
**Альтернатива яку відкинули:** одразу Redis-backed rate limiting зі спільним сховищем між репліками — свідомо не робимо зараз, це окремий тікет #20 (Production Readiness): нова залежність, не MVP-блокер для однорепліковго деплою.

### Реалізація hook: `databaseHooks.user.create.after`, без try/catch

**Рішення:** `src/lib/auth.ts` — `databaseHooks.user.create.after` вставляє рядок в `users` (`authUserId`, `email`, `name` з об'єкта `user`, який хук отримує напряму). Без try/catch навколо insert — помилка має впасти голосно, а не проковтнутись мовчки.
**Чому:** в Better Auth є відкриті issues на GitHub про FK constraint violations і timing-проблеми в `user.create.after` саме при **social login з DB-транзакціями** ([#7260](https://github.com/better-auth/better-auth/issues/7260), [#4614](https://github.com/better-auth/better-auth/issues/4614)). Перевірено наживо через `auth.api.signUpEmail()`: для email/password-флоу (наш поточний єдиний провайдер, `provider_id = credential`) insert відпрацював чисто, `users.auth_user_id` збігся з `auth_user.id` без жодної помилки — тригер тих issues (social login) у нас поки не застосовний.
**Компроміс:** якщо colись додасться OAuth (Google/GitHub — див. запис про account linking в `docs/LEARNING.md`), цей hook треба перетестувати заново саме під тим сценарієм — гарантії "працює для credential" не переносяться автоматично на "працює для OAuth".
**Альтернатива яку відкинули:** обгорнути insert в try/catch з логуванням, щоб уникнути краху sign-up при збої hook. Відкинули — це саме той сценарій розсинхронізації (`auth_user` без `users`), якого hook мав запобігти; тихий catch ховає проблему замість її вирішення.

### Уточнення: hook не атомарний з `auth_user`

**Виправляє:** «Створення запису в `users` — через hook» вище.
**Рішення:** формулювання «hook атомарний і надійний» неточне. `databaseHooks.user.create.after` виконується **після** commit транзакції `auth_user`, не всередині неї — якщо insert у `users` впаде, `auth_user` лишиться без пари.
**Чому:** CodeRabbit на PR #28 дослідив вихідний код Better Auth і показав: after-хуки навмисно чекають commit — це і є фікс issue #7260, де хуки виконувались усередині транзакції й спричиняли FK-помилки. Справжня атомарна альтернатива `afterTransaction` існує лише як ще не змержений PR ([#10231](https://github.com/better-auth/better-auth/pull/10231)); перевірено напряму в `node_modules` — у `better-auth@1.6.18` її фізично немає.
**Компроміс:** ризик приймаємо свідомо. Причин збою кілька — timeout, вичерпання connection pool, права доступу, schema drift, конфлікт `UNIQUE` на email, якщо колись з'явиться шлях створення `users` в обхід хука. Механізму виявлення orphaned `auth_user` немає, але й ніде в застосунку немає retry/reconciliation логіки — це загальний рівень зрілості на MVP-етапі, не унікальний ризик цього хука. Збій буде голосним (наступний запит до профілю впаде), не тихою втратою даних.
**Альтернатива яку відкинули:** ручне обгортання транзакцій навколо `auth.api.signUpEmail()` — ненадійне й version-специфічне, бо Better Auth керує власним connection/transaction контекстом зсередини. Reconciliation-job (фонова перевірка на "сирітські" `auth_user`) — інженерія понад потреби для поточного масштабу; переглянути обидва варіанти, коли `afterTransaction` реально з'явиться в релізі.

### Логін напряму через `/api/auth/sign-in/email`, без кастомної обгортки (симетрично з реєстрацією)

**Рішення:** логін (issue #9) йде через той самий змонтований Better Auth handler і його власний ендпоінт `POST /api/auth/sign-in/email` — без кастомного `/api/auth/login` чи `/api/login`. Жодного додаткового Zod-шару поверх: Better Auth вже валідує форму `email`/`password` на вході.
**Чому:** симетрично з рішенням для реєстрації (запис "Реєстрація напряму через `/api/auth/sign-up/email`" вище) — той самий аргумент застосовується один-в-один: кастомна обгортка додала б шар, який довелось би підтримувати, без реальної користі. Better Auth вже повертає коректні коди на неправильні креденшели (401, підтверджено вручну через `api.http` під час rate-limit тестування). Issue #9 спершу був сформульований як кастомний endpoint симетрично з відкинутим #8 — це виправлено свідомо, не залишено мовчки як розбіжність.
**Компроміс:** так само як і реєстрація — `/api/auth/sign-in/email` стилістично не збігається з рештою плоского REST API (`/accounts`, `/categories`). Успішний логін перевірено наживо (2026-07-28): sign-up → sign-in з правильними креденшелами → `200` + `Set-Cookie: better-auth.session_token` (HttpOnly) → подальший `GET /api/auth/get-session` з цим cookie повертає правильну сесію й користувача.
**Альтернатива яку відкинули:** кастомний `/api/login` з власною Zod-схемою, що викликає `auth.api.signInEmail()` всередині, заради стилістичної консистентності з рештою API — відкинули з тієї ж причини, що й кастомний `/api/auth/register` для реєстрації.

### Уточнення: маршрути тепер у `src/app.ts`, не `src/index.ts`

**Виправляє:** посилання в «Реєстрація напряму через `/api/auth/sign-up/email`» вище.
**Рішення:** після рефакторингу для тестів (issue #10) `src/app.ts` збирає Hono `app` і реєструє всі маршрути, включно з `/api/auth/*`; `src/index.ts` лише імпортує цей `app` і викликає `serve()`.
**Чому:** інтеграційні тести викликають `app.request()` напряму, без реального мережевого порту — для цього `app` має бути експортований без побічного ефекту запуску сервера, стандартний патерн тестованості для Hono.

## Тестування

### Окрема тестова база для інтеграційних тестів, TRUNCATE після кожного тесту

**Рішення:** інтеграційні тести (Vitest, issue #10) йдуть проти `TEST_DATABASE_URL` (окрема база `personal_api_test`), не проти dev-бази. `vitest.config.ts`: `globalSetup` (`src/test/global-setup.ts`) мігрує тестову базу один раз перед усім прогоном; `setupFiles` (`src/test/env-setup.ts`, потім `src/test/db-cleanup.ts`) підміняють `DATABASE_URL` на `TEST_DATABASE_URL` для кожного тестового файлу і чистять усі таблиці (`TRUNCATE ... CASCADE`) після кожного окремого тесту.
**Чому:** без ізоляції кожен прогін тестів лишав би рядки в базі, якою розробник користується вручну (Drizzle Studio, `api.http`) — саме це вже сталось раніше з `test@example.com`/`manual-test@example.com`: сирітські рядки в `auth_user`, створені до появи `onUserCreate` хука, які довелось вручну шукати й видаляти. Окрема тестова база також наперед сумісна з майбутнім CI (issue #22), де жодної "спільної dev-бази" не існує в принципі.
**Компроміс:** другий `DATABASE_URL` в `.env`/`.env.example`, трохи складніша конфігурація Vitest (три файли в `src/test/` замість нуля). `TRUNCATE ... CASCADE` після кожного тесту простіше, ніж transaction-rollback-патерн, але не такий швидкий — прийнятно при поточній кількості тестів.
**Альтернатива яку відкинули:** та сама dev-база з ручним очищенням чи унікальними email без прибирання — відкинули: перший варіант крихкий (тест, що впав до кроку очищення, лишає сміття — той самий провал, що вже стався з хуком), другий не масштабується на CI і безкінечно роздуває dev-базу. Transaction-rollback (кожен тест — відкотена транзакція) відкинули теж: Better Auth керує власним connection-контекстом зсередини (той самий нюанс, що й у "Реалізація hook" вище), і змусити її долучитись до зовнішньої тестової транзакції ненадійно й version-специфічно.

### Уточнення: конфіг Vitest розділено на два проєкти

**Уточнює:** «Окрема тестова база для інтеграційних тестів» вище.
**Рішення:** `globalSetup`/`setupFiles` більше не ключі верхнього рівня — вони переїхали всередину проєкту `app` (`include: ['src/**/*.test.ts']`). Поруч зʼявився проєкт `scripts` (`include: ['scripts/**/*.test.mjs']`) **без** бази, без `globalSetup` і без `setupFiles`. Спільний `exclude` — `[...configDefaults.exclude, '.claude/**']`.
**Що стало неправдою:** запис вище описує `setupFiles` як такі, що працюють «для кожного тестового файлу», і називає обидва ключі верхньорівневими. Для тестів під `scripts/` це хибно. Саме рішення про окрему тестову базу лишається чинним у повному обсязі — для проєкту `app`.
**Чому розділили:** тести інструментів не торкаються ні мережі, ні диску поза temp, а платили `TRUNCATE` після кожного кейсу і не могли запуститись без піднятого Docker — найдешевші тести в репозиторії стояли за найважчою залежністю. **Виграшу в часі це майже не дає** (заміряно: `--project app` 11.45 с, повний прогін 12.35 с); падіння з ~22 с до ~12 с дав `exclude` нижче. Записано явно, бо число легко приписати не тій причині.
**Чому `exclude` саме в проєктах:** з визначеними `projects` Vitest ігнорує `exclude` верхнього рівня — перевірено decoy-тестом. Claude Code тримає worktree агентів у `.claude/worktrees/`, тобто **другу повну копію `src/`**, і дефолтний `include` її підхоплював: `npm test` мовчки ганяв застарілі інтеграційні тести проти тієї ж `TEST_DATABASE_URL` і рапортував 48 тестів, де справжніх було 27. Спред поверх `configDefaults.exclude`, а не заміна, щоб не втратити власні виключення Vitest.
**Реалізація:** #71 (знайдено при рев'ю, не планувалось).

### Уточнення: проєктів Vitest три, а не два

**Уточнює:** запис вище.
**Рішення:** поруч із `app` і `scripts` зʼявився третій проєкт — `hooks` (`include: ['.claude/hooks/**/*.test.mjs']`). Він єдиний виключає `.claude/worktrees/**` поіменно, а не всю теку `.claude/**`.
**Чому знадобився:** спільний `exclude` викидає `.claude/**` цілком, а тести хука лежать усередині `.claude/hooks/`. Коли в гілку #76 влився свіжий `main`, вони перестали потрапляти в будь-який `include` і зникли з `npm test` — мовчки, лишаючись зеленими при прямому запуску. Помітила це не збірка, а звірка конфігу очима.
**Чому не звузили спільний `exclude`:** `app` і `scripts` від цього не виграють нічого (їхні `include` до `.claude/` не дотягуються), а зміна зачепила б захист, який щойно довів свою потрібність. Ціна: дві майже однакові константи, які треба тримати в кроці.
**Заразом виправлено:** `tsconfig.scripts.json` тепер включає й `.claude/hooks/**/*`. Виняток «plain JavaScript під `checkJs`» діяв для обох тек, але `include` покривав лише одну, тож код хука був нетипізованим. На першому ж прогоні `checkJs` дав 16 неявних `any` і місце, де `matchAll` міг покласти `undefined` у список імен npm-скриптів.
**Реалізація:** #76.

## CRUD-ендпоінти та захист доступу

### Middleware резолвить сесію в доменного `users`, не `auth_user`

**Рішення:** `src/middleware/auth.ts` (`requireAuth`, issue #30) бере Better Auth сесію (`auth.api.getSession`), потім шукає відповідний рядок `users` за `authUserId`, і саме доменний `users`-рядок (не auth-user) кладе в Hono context (`c.set('user', ...)`). Якщо рядка `users` немає — кидає помилку, не повертає 401 і не ковтає її в try/catch.
**Чому:** `accounts.userId` (і майбутні `categories`/`transactions`/`budgets`) посилаються на `users.id`, не на `auth_user.id` — різні простори id (uuid проти тексту). Якщо профілю `users` немає (хук не спрацював — див. dual-write запис вище), сесія технічно дійсна, але акаунт у зламаному стані — це проблема цілісності даних, не "невірні креденшели", тому падає голосно, за тим самим принципом, що й сам хук.
**Альтернатива яку відкинули:** класти `session.user` (auth-user) напряму в контекст і шукати `users`-рядок окремо в кожному route-handler — відкинули, бо дублювало б той самий запит у кожному майбутньому CRUD-модулі (categories/transactions/budgets), рівно те, для чого й заводили спільний middleware (issue #30).

### Доступ до чужого ресурсу — 404, не 403

**Рішення:** `GET/PATCH/DELETE /accounts/:id` повертає `404`, коли рахунок належить іншому користувачу — так само, як і коли id взагалі не існує в базі. Окремого 403 "заборонено" немає.
**Чому:** той самий anti-enumeration інстинкт, що й у email-реєстрації (див. запис вище): 403 підтвердив би, що ресурс з таким id існує, просто не твій — 404 не видає нічого зайвого. Той самий патерн застосується до categories/transactions/budgets.
**Компроміс:** легітимний власник, що помилився в id, і той, хто намагається вгадати чужі id, отримують однакову відповідь — з відповіді API неможливо відрізнити "не існує" від "не твоє", і це навмисно.

### Уточнення: валюта рахунку незмінна після створення

**Уточнює:** «Мультивалютність: `char(3)` ISO-4217» вище.
**Рішення:** `PATCH /accounts/:id` не приймає поле `currency` — воно відсутнє в `updateAccountSchema`, а не просто необов'язкове. Схема побудована через `z.strictObject`, тому `currency` в тілі PATCH повертає `422`, а не ігнорується мовчки.
**Чому:** issue #36 виносить «зміну валюти вже створеного рахунку» в Out of scope, але вихідний `updateAccountSchema = createAccountSchema.partial()` цього не відображав — успадковував усі поля, включно з `currency`. Реалізований мовчки Out of scope — те саме розходження коду з рішенням, від якого застерігає цей файл, і непомічене за тестами, бо жоден тест на це поле не цілився.
**Компроміс:** `z.strictObject` заразом забороняє будь-яке незнайоме поле в PATCH-тілі, не тільки `currency`. Узгоджується з рештою проєкту — падати голосно, а не ігнорувати мовчки.
**Альтернатива яку відкинули:** лишити `currency` у схемі й просто не документувати, що зміна «не підтримується».
**Реалізація:** #36.

### Уточнення: незмінність валюти рахунку — лише на рівні застосунку, свідомо

**Уточнює:** «Валюта рахунку незмінна після створення» вище.
**Рішення:** *формат* валюти захищений двома незалежними шарами (`char(3)` + `CHECK` у базі, Zod-enum на межі), а *незмінність* — лише одним, `updateAccountSchema`. Прямий `UPDATE accounts SET currency = 'EUR'` — з `db:studio` чи майбутнього скрипта міграції даних — пройде без помилки.
**Чому:** інваріанта дорожча за формат: зміна валюти миттєво переоцінює всю історію транзакцій рахунку (транзакція успадковує валюту, а не зберігає власну), і робить це мовчки — той клас помилки, який `API-CONVENTIONS.md` §6 називає найдорожчим. Симетричний `BEFORE UPDATE`-тригер розглядався і відхилений: він додає сутність бази, яку треба тестувати й супроводжувати окремо від Drizzle-схеми, заради інваріанти, якої сьогодні жоден шлях у коді не порушує.
**Компроміс:** ручний `UPDATE` в обхід застосунку лишається способом мовчки зламати інваріанту. Прийнятно — той самий ризик існує для будь-якого поля, не захищеного тригером.
**Реалізація:** #36 (документує наявний стан, коду не змінює).

## CI

### GitHub Actions: один job, три послідовні кроки

**Рішення:** `.github/workflows/ci.yml` — один job `ci` на `ubuntu-latest`, кроки `npm ci` → `npm run typecheck` → `npm run lint` → `npm test`. Тригери: `pull_request` (будь-яка цільова гілка) і `push` у `main`.
**Чому:** `npm ci` коштує більше часу, ніж усі три перевірки разом, тому три паралельні job'и повторили б checkout + install тричі заради виграшу в кілька секунд. Один job — це ще й одна назва status check, яку branch protection вимагає в одному правилі; три job'и означали б три обов'язкові перевірки, які легко розсинхронізувати з реальним складом workflow. `push` у `main` перевіряється окремо від PR навмисно: merge-комміт — це код, якого жоден прогін ще не бачив, і два PR, зелені кожен окремо, можуть зламати `main` разом.
**Компроміс:** кроки послідовні — падіння `typecheck` ховає, чи пройшли б `lint` і `test`. Одна ітерація фідбеку замість повного списку проблем одразу.
**Альтернатива яку відкинули:** окремі job'и `typecheck`/`lint`/`test`, що йдуть паралельно — відкинули за співвідношенням ціни (три install-и) до виграшу при поточному розмірі проєкту. Варіант `if: always()` на кожному кроці (щоб зібрати всі падіння за один прогін) відкинули теж: він робить «job впав» і «крок впав» різними речами, і читати результат стає складніше, ніж запустити `npm run lint` локально.
**Реалізація:** issue #22.

### Postgres у CI — service container, не `docker compose up`

**Рішення:** база для тестів у CI піднімається як GitHub Actions service container (`postgres:16-alpine`, health-check `pg_isready`) — той самий мажор, що в `docker-compose.yml`. Redis у CI не піднімається взагалі.
**Чому:** runner уміє сам дочекатись, поки контейнер стане healthy, перед першим кроком — з `docker compose up` довелось би вручну опитувати готовність, інакше `npm test` стартує раніше, ніж Postgres приймає з'єднання. Той самий мажор, що локально, — щоб зелений пайплайн не означав «зелено на іншій базі». Redis нікому в тестах не потрібен: rate limiting поки in-memory, черг ще немає.
**Компроміс:** порт відрізняється — локально `5433` (щоб не конфліктувати з чужим Postgres на машині розробника), у CI `5432`. Тому `TEST_DATABASE_URL` заданий у workflow окремим рядком, а не взятий з якогось спільного файлу: два середовища, два значення, і це видно.
**Альтернатива яку відкинули:** запускати в workflow той самий `docker compose up -d postgres`, щоб CI і локальна машина читали один файл — відкинули: compose-файл параметризований через `.env` (`${POSTGRES_USER}` і решта), якого в CI немає й не має бути, і тягне за собою redis.

### CI використовує той самий `global-setup.ts`, окремого кроку міграцій немає

**Рішення:** workflow не викликає `npm run db:migrate` і не має жодного CI-специфічного кроку підготовки бази. `TEST_DATABASE_URL` вказує на `personal_api_test`, якої у свіжому контейнері не існує — `src/test/global-setup.ts` створює її, накочує міграції й чистить таблиці, тим самим кодом, що й локально. `DATABASE_URL` у workflow навмисно не заданий.
**Чому:** окремий крок міграцій у CI — це друга гілка логіки бутстрапу, яка розходиться з локальною тихо: локально зелено, у CI червоно (або навпаки), і причина не в коді, а в тому, що дві гілки готують базу по-різному. Заразом це перевірка `ensureDatabaseExists` на його ж сценарії — «бази ще немає», який локально трапляється раз на життя volume. Про `DATABASE_URL`: `src/test/env-setup.ts` виводить його з `TEST_DATABASE_URL` сам, а `assertNotDevDatabase` навмисно падає, коли обидва вказують на одну базу — задати його в workflow означало б або дублювати те, що код робить сам, або впертись у цю перевірку.
**Компроміс:** CI мовчки залежить від того, що користувач із `TEST_DATABASE_URL` має право на `CREATE DATABASE` (в офіційному образі `POSTGRES_USER` — суперкористувач). Якщо колись знадобиться обмежений користувач, CI зламається не там, де цю зміну зроблять.

### `BETTER_AUTH_SECRET` — repository secret, не літерал у workflow

**Виправлено:** див. «Уточнення: `BETTER_AUTH_SECRET` у CI — таки літерал» нижче. Чинне рішення — літерал.
**Рішення:** workflow бере `BETTER_AUTH_SECRET` з `${{ secrets.BETTER_AUTH_SECRET }}`. `BETTER_AUTH_URL` лишається звичайною env-змінною прямо в yaml.
**Чому:** тести нічим справжнім не підписують, тож спокуса вписати рядок прямо у workflow велика — але секрет, закомічений «тільки для тестів», це рівно той, який потім скопіюють туди, де він щось значить. `BETTER_AUTH_URL` ховати нема від кого — це публічна базова адреса.
**Компроміс:** GitHub не передає секрети в прогони з форків, тож такий PR упаде на `npm test` з повідомленням про довжину секрета, а не з поясненням, що секрета не дали. З появою зовнішніх контриб'юторів правильний вихід один — віддати тестове значення літералом, бо воно й так нічого не захищає.
**Чого робити не можна:** переводити workflow на `pull_request_target`, щоб секрети доїхали до форків. Цей тригер виконується в контексті базового репозиторію, тож `checkout` коду з форку плюс `npm test` віддає чужому коду і секрети, і токен із правами на запис. Це класичний «pwn request». Секрети недоступні форкам навмисно.

### Уточнення: `BETTER_AUTH_SECRET` у CI — таки літерал

**Виправляє:** «`BETTER_AUTH_SECRET` — repository secret, не літерал у workflow» вище.
**Рішення:** `ci.yml` більше не читає `${{ secrets.BETTER_AUTH_SECRET }}`. Тестове значення стоїть літералом, написаним так, щоб його не можна було прийняти за робочий секрет (`ci-only-not-a-real-secret-…`).
**Чому:** запис вище сам назвав цей вихід у своєму «Компромісі», але чекав його від форків — прийшло раніше й з іншого боку. PR від Dependabot виконуються з окремим сховищем секретів (Settings → Secrets → Dependabot), тож `secrets.BETTER_AUTH_SECRET` приїхав порожнім рядком, і обидва перші PR бота (#66, #67) впали з «BETTER_AUTH_SECRET must be at least 32 characters». Наслідок гірший за червоний прогін: пін action-ів на SHA лишився без механізму, який тримає його свіжим.
**Альтернатива яку відкинули:** продублювати секрет у Dependabot secrets. Прогін би позеленів, але це віддало б справжній секрет рівно тим запускам, від яких GitHub ізолював його навмисно.
**Компроміс:** у workflow лежить рядок, який на вигляд є секретом, і правило «не комітити секрети» отримало видимий виняток. Тримається він тільки на тому, що значення самопояснювальне; справжній секрет у CI буде вже іншим рішенням і окремим записом.

### Зовнішні залежності workflow — action-и на commit SHA, образ Postgres на тег

**Рішення:** `actions/checkout` і `actions/setup-node` зафіксовані повним commit SHA, людська версія — в коментарі поруч. `postgres:16-alpine` лишається тегом. `actions/checkout` викликається з `persist-credentials: false`.
**Чому:** тег в Actions рухомий — власник може перевести його на інший комміт, і тоді в нашому job'і виконується вже інший код, з нашим токеном і секретами; саме так у 2025-му обернули проти користувачів `tj-actions/changed-files`. SHA підмінити не можна, не змінивши сам SHA. `persist-credentials: false` — з тієї ж родини: `checkout` за замовчуванням лишає `GITHUB_TOKEN` у `.git/config`, а кожен наступний крок виконує код із PR-гілки (lifecycle-скрипти npm, файли тестів). Цей workflow нікуди не пушить, тому токену там нема чого робити.
**Компроміс:** запінений SHA не оновлюється сам — пін без автооновлення через рік означає версію без свіжих патчів, тобто навпаки до того, заради чого його ставили. Тому разом із піном заведено `.github/dependabot.yml` (`github-actions`, `monthly`): два action-и дають ~2–6 PR на рік, кожен проходить цей самий CI. Ціна, яка лишається: PR від бота треба читати, а не мерджити наосліп. Екосистему `npm` навмисно не додано — інший порядок шуму й окреме рішення.
**Альтернатива яку відкинули:** пінити й `postgres:16-alpine` на `@sha256:` (пропозиція CodeRabbit на PR #65). Відкинули: саме тег тримає CI на тому ж мажорі, що `docker-compose.yml`, а дайджест прив'язав би CI до однієї арх-специфічної збірки й дозволив би двом середовищам розійтись тихо. Це не production-образ, а контейнер з одноразовими даними, що живе хвилини.

### Перевірка шляхів у конфігах тулінгу

**Рішення:** `scripts/check-config-paths.mjs` + окремий job `config-paths` валять збірку в трьох випадках: `path:` у `.coderabbit.yaml` або патерн у `knowledge_base.code_guidelines.filePatterns` не збігається з жодним відстежуваним файлом; кореневий `*.config.*` не входить у програму жодного з двох tsconfig; зникла прив'язка контракту — порожній `filePatterns` або `code_guidelines.enabled`, що не `true`. Останній гейт саме про присутність ключа: перша редакція ловила лише оголошений і нечитабельний ключ, тож видалення всього блоку `knowledge_base` проходило зелено, і `docs/API-CONVENTIONS.md` знову ставав невидимим для CodeRabbit. Охоплення рахується за правилами самого TypeScript (`include` мінус `exclude`, плюс `files`, який `exclude` не фільтрує) — файл, вибитий через `exclude`, не компілюється, а за одним `include` виглядав охопленим. Перевіряється тільки існування шляху; чи правильна сама інструкція — лишається за рев'ю.

**Чому:** `.coderabbit.yaml` від першого комміту (`ed56429`, 13 червня) скоупив інструкцію про валідацію env і хардкод секретів на `src/config/**` — теку, якої не було ніколи. Найбільш чутлива з безпеки інструкція рецензента два місяці не застосовувалась ні до чого й не могла подати сигналу: глоб, який ні з чим не збігається, — валідний YAML. Той самий клас помилки жив у tsconfig: `drizzle.config.ts` і `vitest.config.ts` не входили в `include` жодного конфігу, і зелений `npm run typecheck` про них мовчав.

**Компроміс:** читач `.coderabbit.yaml` рядковий, не YAML-парсер — у Node немає вбудованого YAML, а сенс джоба в тому, щоб працювати без `npm ci` за секунди. Конфіг у flow-стилі прочитається для нього порожнім, тому «оголошено ключ, розібрано нуль записів» трактується як провал. Ціна: при зміні форми конфігу треба чіпати й читач.

**Наслідок для «TypeScript, без винятків»:** до `include` в `tsconfig.scripts.json` додався `eslint.config.js` — третій файл на звичайному JavaScript поза двома теками, яким виняток видавався початково. Підстава та сама (конфіг репозиторію, який має типізуватись), `checkJs` тримає його під тими самими strict-правилами.

**Спільний код — за правилом трьох:** `formatCause` і форма `report` дослівно збігаються з `check-conformance-markers.mjs`. Модуль не заводимо, поки скриптів два — `scripts/lib/` з однією функцією на два викликачі дає більше зв'язності, ніж економить. **Тригер на витяг — третій скрипт перевірки.**

**Альтернатива яку відкинули:** глоб `*.config.*` у корені замість переліку трьох файлів. Відкинули: у корені лежать і `docker-compose.yml`, і дотфайли, тож патерн, достатньо широкий для майбутнього конфігу, ловив би і все інше.

**Реалізація:** #77.

## Відкладені рішення (заплановано на Фазу 2+)

### Merchants — окрема сутність, не в MVP

**Ідея:** таблиця `merchants` (`user_id`, `name`, `icon`) + `merchant_id` в `transactions` — щоб не повторювати вибір іконки для одного й того ж магазину при кожній транзакції.
**Чому відкладено:** для MVP категорій з іконками достатньо. Merchants стане особливо доречним разом з банківською інтеграцією — Monobank/Privat повертають MCC-коди і назви мерчантів автоматично.

### Банківська інтеграція (Monobank / Privat API)

**Ідея:** підключити `accounts` до банківських API для realtime синхронізації транзакцій; ручне управління лишається тільки для готівки.
**Підготовка зараз:** заплановані поля `external_id`, `external_source` в `accounts` — додаються окремою міграцією одразу після базової схеми.
